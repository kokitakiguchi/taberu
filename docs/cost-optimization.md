# AI コスト最適化メモ（将来の改善候補）

Taberu の Claude API 利用コストを下げるための候補をまとめる。
本ファイルは「検討用の棚卸し」です。`nutrition_label` の Haiku 切替だけ実装済みで、それ以外は未実装です。
着手するときは各項目を個別タスク化し、効果をサンプルで確認してから本体に統合する
（[.claude/rules/ai-integration.md](../.claude/rules/ai-integration.md) / [learning-track.md](../.claude/rules/learning-track.md) に従う）。

## 現状の AI 利用（2026-06-05 時点）

| モード | 入力 | モデル | 備考 |
|--------|------|--------|------|
| `dish_photo` | 画像（Vision） | `claude-3-5-sonnet-20241022` | 料理を推定 |
| `nutrition_label` | 画像（Vision） | **`claude-haiku-4-5-20251001`** | ラベルの記載値読み取り（安価モデルへ切替済み） |
| `text_ai` | テキスト | `claude-3-5-sonnet-20241022` | 料理名・説明から推定 |
| `text_manual` | なし | — | API 呼び出しなし |

モデル実装の正本：`backend/src/services/ai.rs`（`MODEL_DEFAULT` / `MODEL_LABEL`）、
画像保存・リサイズは `backend/src/services/storage.rs`。

## 改善候補

各項目に **効果 / 実装コスト / リスク** を併記する。優先度は「効果 ÷ 実装コスト」で判断。

### 1. 画像のダウンスケール強化（効果：大 / 実装コスト：中 / リスク：低〜中）

- 現状 `storage.rs` は **5MB 超のときだけ** リサイズしている。
- Vision のトークン課金は概ね画素数に比例する（目安：`tokens ≒ 幅 × 高さ / 750`）。
- 送信前に **常に長辺 ~1568px（~1.15MP）以下** へ縮小すると、dish_photo・nutrition_label
  双方の Vision 入力トークンを大きく削減できる。
- 案：保存用の原本はそのまま、**Claude 送信用の縮小版を別途生成** して base64 化する
  （現状は保存物と送信物が同一）。
- リスク：縮小しすぎるとラベルの細かい数字が潰れて読み取り精度が落ちる。
  ラベルは文字が小さいので、最低保証解像度を設けるか dish_photo より緩い縮小率にする。

### 2. text_ai を安価モデルへ（効果：中 / 実装コスト：小 / リスク：低）

- `analyze_text`（画像なし・テキストからの推定）は比較的軽いタスク。
- Haiku 系（`MODEL_LABEL` と同等）で十分な品質が出る可能性が高い。
- 実装：`analyze_text` のモデルを `MODEL_DEFAULT` から専用定数に分けるだけ。
- リスク：推定の質が下がる可能性。数件のサンプルで Sonnet と比較してから切替える。

### 3. dish_photo のモデル再評価（効果：中 / 実装コスト：小 / リスク：中・要検証）

- 現行 `claude-3-5-sonnet-20241022` は旧世代。最新の Sonnet 4.x / Haiku 4.5 で
  コストと品質のバランスを再評価する。
- 料理推定は精度影響が大きい（栄養値がブレる）ので、**必ずサンプル画像で品質比較** してから変更。
- リスク：安易に Haiku 化すると推定精度が落ちる。dish_photo は慎重に。

### 4. プロンプトキャッシュ（効果：中・呼び出し量が増えたら / 実装コスト：中 / リスク：低）

- `JSON_SCHEMA` + `PROMPT_SUFFIX` の **静的部分を system プロンプト化** し、
  `cache_control`（prompt caching）を付ける。
- 呼び出し頻度が上がるほど入力トークン課金を削減できる（キャッシュヒット分が割引）。
- シングルユーザー・低頻度の現状では効果は限定的。利用が増えてから着手で十分。

### 5. max_tokens の見直し（効果：小 / 実装コスト：小 / リスク：低）

- 出力は小さな JSON のみ。現状 `max_tokens: 1024`。
- 実出力に見合う値（~512 程度）へ下げ、出力課金の上限を抑える。
- リスク：アレルゲンが多い等で JSON が切れるとパース失敗 → 既存フォールバックに落ちる。
  余裕を見た値にする。

### 6. 開発時のモックモード徹底（効果：運用 / 実装コスト：なし / リスク：なし）

- 既存の `CLAUDE_MOCK=1`（`config.rs`）を開発・テストで常用し、実 API 呼び出しを最小化する。
- 実 API は「サンプル画像で 1〜3 回」に留める運用を継続（ai-integration.md の方針どおり）。

## やらないと決めたこと

- **ローカル OCR（Tesseract 等）の導入**：ネイティブ依存（tesseract/leptonica）追加と
  日本語ラベルの精度検証が重く、「安価モデルで Vision 維持」で目的を満たせるため見送り
  （2026-06-05 判断）。さらにコストを詰める必要が出たら「ローカル OCR + 安価テキストモデル」
  を上記候補と合わせて再検討する。
